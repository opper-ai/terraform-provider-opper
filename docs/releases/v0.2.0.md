# Opper Terraform provider v0.2.0

Adds atomic initial project access and runtime-key IP allowlists to the existing 11 resources and nine data sources. Includes release-note handling and documentation-link fixes.

## New configuration

- **`opper_project.initial_access`** creates the project and initial Organization or Restricted policy atomically through the dedicated `/management/v1/projects/with-access` endpoint. Role and member references may resolve during apply. The attribute records creation history; metadata refresh and updates do not reconcile current policy drift. Existing/imported projects cannot gain a creation snapshot, and changing one is rejected without replacement. Removing it forgets only that history. Use explicit import into `opper_project_access` and a separate plan for ongoing policy management.
- **`opper_api_key.allowed_ips`** creates runtime-key restrictions atomically and updates public IP/CIDR lists without rotating the key ID or secret. Omission/null preserves the observed list on existing keys during refresh and in-place updates; `[]` clears restrictions. Runtime authentication caches can delay enforcement by up to one minute.

Both backend contracts are deployed in EKS and Evroc. Initial access requires `projects:write` and `project_access:write`, in addition to the ordinary project read/delete scopes for its lifecycle. Custom-role dependencies retain their Enterprise and role-scope requirements. IP allowlists use the existing `apikeys:read` and `apikeys:write` scopes.

## Upgrade

Use Terraform 1.11 or later. Update the provider constraint and run `terraform init -upgrade`:

```hcl
terraform {
  required_version = ">= 1.11"

  required_providers {
    opper = {
      source  = "opper-ai/opper"
      version = "~> 0.2.0"
    }
  }
}

provider "opper" {}
```

The `~> 0.1.0` constraint does not select v0.2.0. Existing configurations can continue omitting both new attributes, subject to the restricted-key replacement requirement below. Installation does not convert project policies or change key restrictions.

**Explicitly configure the allowlist before replacing a restricted key.** Use a fully known current or new list, or `[]` to intentionally clear restrictions. Computed values are not a carry-forward guarantee during replacement. Normal project/name/rotation/idempotency changes reject an omitted or unknown policy before mutation. Terraform Core's manual replacement and taint decisions are outside that guard; configure the list before `-replace`, taint replacement or recovery. Use a fresh `idempotency_key` for every replacement if one is configured.

Projects with `initial_access` still delete normally, including revoking their runtime keys. Removing creation history does not remove the remote policy; preserve any custom-role dependencies needed for correct destroy order. Runtime secrets remain sensitive values stored in Terraform state.
